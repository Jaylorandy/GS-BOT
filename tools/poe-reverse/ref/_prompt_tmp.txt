layout_type meanings:
  line_items   - one row per style/colour/size with a quantity (e.g. LPP SA).
  matrix_2axis - colour blocks, each a size x inseam grid (e.g. COLIN'S trousers).
  matrix_1axis - colour blocks, each a single row of sizes (e.g. SAKHA).

"has_color_total" / "has_size_total": whether the document prints SUBTOTALS the
  system can cross-check its own extraction against.
    * line_items layouts print ONLY a block GRAND TOTAL - set BOTH to false.
    * matrix (colour-grid) layouts print a per-row/per-colour TOTAL column and a
      bottom TOTAL row per size -> set BOTH to true.
  When unsure, true is the safer choice (the system still verifies the totals
  agree with what it parses before trusting them).

HARD RULES - breaking any of these makes the whole answer useless:

1. "raw_line" MUST be copied character-for-character from the document text
   below: same tokens, same order, same spelling, single spaces between tokens.
   Do NOT reformat, translate, abbreviate, re-order or "clean up" anything.
   This string is used to find the row again in the document.

2. List EVERY order block in "orders" with its "po_no" and its
   "block_total_qty" - none may be omitted; these totals are the reference the
   system checks its own extraction against.
   Order LINES, by contrast, are only a REPRESENTATIVE SAMPLE - just enough to
   infer the row structure. Report AT MOST 8 lines per order block AND AT MOST
   24 lines for the WHOLE document (fewer is fine). When a document has many
   blocks, sample a few lines from a couple of blocks and leave "lines" empty
   for the rest - the blocks repeat the same row structure, and the system
   extracts every row itself from the document. Prefer rows that differ in
   shape over near-identical ones.
   Always report "block_total_qty" (the printed total for that PO, its TOTAL row).
   A total row is often UNLABELLED and prints two numbers - the QUANTITY first,
   the MONEY amount second, matching the column header "... Quantity Price
   Total Amount". For "8000 81,600.00" the block_total_qty is 8000, NOT 81600:
   the token carrying decimals is money, never a quantity. Quantities are whole
   pieces, so block_total_qty must equal the sum of that block's line
   quantities - check it before you answer.

3. A REAL order line is a PRICED DETAIL ROW: it carries a description/colour
   block AND a unit price. Example:
       637JO-80X-S MEN`S TROUSERS 80X 80X BEIGE PCS 744 10.20 7,588.80
   These look-alike rows are NOT order lines - never report them:
     * pack break-up rows, e.g.  637JO-80X-T01 PACK 2 186 372
       (the "2" is pieces-per-pack, not an ordered quantity)
     * bare sub-breakdown rows, e.g.  637JO-80X-S PCS 372
       (no description, no colour, no unit price - a partial restatement)
     * TOTAL / SUBTOTAL / SUMMARY / grand-total rows.

4. "qty" is a plain integer, no thousands separator. "unit_price" is a plain
   number (e.g. 10.20 not "$10.20"). Report unit_price for EVERY order line
   that shows one - it is the per-piece price of that SKU/colour/size. If the
   document prints a UNIT PRICE column or a per-line price token, include it.
   If the document does not print unit prices at all for a given line, use null
   (the system will then use the header-level price if one is available).

5. TOTALS use European number format: a DOT groups thousands, a COMMA is the
   decimal point. "26.000" = 26000 pieces, "1.234" = 1234, "158,00" = 158.00.
   When you report "block_total_qty" (or any "qty") copy the full integer the
   printed TOTAL row shows - "26.000" must be reported as 26000, never as 26.

6. Group the lines under the order (PO) they belong to. A document that repeats

   holds a single order, return one element in "orders".
