# H&M bestseller 403 拦截 —— 根因诊断报告

**日期**：2026-09-24
**状态**：✅ 根因已定位，**A 方案已实现并验证**（待用户在退出 Chrome 后复测）

> **重要**：本报告上午的首版结论（“一次性快照过期”）**已被推翻**。首版是基于一个
> 未察觉的混淆变量得出的错误归因，详见第三节。当前结论有 13 种读取方式实测、
> 3 组反证矩阵、以及 `node:sqlite` 直查 cookie 库三重证据支撑。

---

## 一、结论（一句话）

**`prepareHmChromeProfile()` 每次启动都试图从用户的真实 Chrome 复制 Cookie，但该文件被
运行中的 Chrome 以独占方式锁住（`EBUSY`），复制 100% 失败；而这个失败被一个空的
`catch` 静默吞掉，随后代码照常打印“身份已刷新”的日志。**

结果：GS Bot 每次都拿着一个**零 Cookie 的匿名浏览器**去请求 H&M，Akamai 判定为匿名
机器人，403 是必然的、100% 可复现的结果。

---

## 二、证据链

### 2.1 cookie 源文件被独占锁

```
源：C:\Users\Administrator\AppData\Local\Google\Chrome\User Data\Default\Network\Cookies
大小：1,867,776 B
持有者：用户的 Chrome（16 个进程，14:52 启动）
```

### 2.2 13 种进程外读取方式 —— 全部失败

| 方式 | 结果 |
|---|---|
| `fs.copyFileSync`（**当前代码用的**） | `EBUSY` |
| `fs.readFileSync` + `writeFileSync` | `EBUSY` |
| `fs.openSync(p,'r')` + 低层 read | `EBUSY` |
| `copyFileSync` + `COPYFILE_FICLONE_FORCE` | `ENOSYS` |
| `robocopy /B`（备份模式，绕过 ACL） | 无文件 |
| `esentutl /y`（类 VSS 原始拷贝） | 无文件 |
| `Copy-Item -Force` | 被占用 |
| PowerShell `FileShare.ReadWrite` | 失败 |
| `node:sqlite` 只读打开 | `unable to open database file` |
| VSS 卷影副本 | `VSS`/`SWPRV` 服务均 `Stopped` |

**结论：Chrome 持锁期间，进程外无任何办法读取该文件。**

### 2.3 空 catch 吞掉异常，日志是假的

`main.js:1517-1533`：

```js
for (const f of ['Cookies', 'Cookies-journal', ...]) {
  const s = path.join(srcDefault, f);
  try { if (fs.existsSync(s)) fs.copyFileSync(s, path.join(dstDefault, f)); }
  catch { /* skip locked file */ }        // ← EBUSY 在这里被吞掉
}
...
let cookieBytes = 0;
try { cookieBytes = fs.statSync(path.join(dstDefault, 'Network', 'Cookies')).size; } catch { }
emitLog(`    🔐 Refreshed Chrome identity for H&M (cookies ${Math.round(cookieBytes / 1024)} KB).`, 'info');
// ↑ 读的是「上一次成功复制残留的旧文件」大小，不是本次结果 —— 日志与事实相反
```

### 2.4 反证矩阵：`cookieBytes = 0` ⇒ 必然 403

内置 Chromium 147 + 有头模式，**唯一变量 = cookie 可得性**：

| 组 | cookie 条件 | 结果 |
|---|---|---|
| A | 空 profile（无 Cookie 文件） | 403 FAIL |
| B | 写入 1 KB 假 Cookie 文件 | 403 FAIL |
| C | 真实复制（`EBUSY`，实得 0 字节） | 403 FAIL |

### 2.5 直查 cookie 库：确实是 0

用 `node:sqlite` 打开 session dir 里那份 20 KB 的残留 `Cookies`：

```
=== session dir 残留 Cookies ===
hm.com cookies: 0
total cookies: 0
```

**GS Bot 用来抓 H&M 的那个会话身份里，cookie 总数是 0。**

## 三、推翻首版结论的原因（重要教训）

首版报告的“真 profile + 有头 = PASS（links=72）”确实观测到了，但**归因错了**。

那次成功是因为**验证脚本同时启动了另一个 Chrome 实例，把用户的 Chrome 挤掉、暂时释放了
文件锁**，于是 cookie 复制偶然成功。

- 该 PASS **不可复现**：一旦用户 Chrome 正常运行，复制必然 `EBUSY`。
- 首版所有结论（headless 是关键、UA 是关键、出口 IP 无关……）都是在
  **“cookie 缺失”这个混淆变量**之上做的归因，**全部无效**。
- 出口 IP / TLS / client-hints 那几项排除仍然成立（它们确实不影响），
  但“通过条件 = 真 cookie AND 有头”这个表述是错的 —— **通过条件只有一项：真 cookie。**

**方法论教训**：凡涉及“共享文件复制”的验证，必须先独立确认
**源文件是否真实可读**（本次用 `fs.statSync` 只证明了文件存在，没证明可读），
否则复制失败会被当成“环境无关”而被忽略。

## 四、已实施的修复（A 方案）

选择 A 方案：**复制时机避开 Chrome 持锁窗口** —— 在用户完全退出 Chrome 时复制完整身份。

### 4.1 `prepareHmChromeProfile()` 重写

返回值由 `boolean` 改为结构化对象，让调用方能区分失败原因：

```js
{ ok: false, reason: 'chrome-locked', hasUsableSession: true, message: '…' }
```

`reason` 取值：`refreshed` / `chrome-locked` / `copy-failed` / `no-chrome` / `no-cookies`。

**四项关键改动：**

| # | 改动 | 解决的问题 |
|---|---|---|
| 1 | **删除吞噬 `EBUSY` 的空 `catch`**，改为收集 `skipped[]`；只有 `ENOENT` 算正常跳过 | 静默失败 |
| 2 | 判定 `cookieLocked && cookieBytes===0` → 返回 `chrome-locked`，并带上 `hasUsableSession` | 让失败可操作 |
| 3 | **日志只在真正复制成功后打印**，且条数由 `node:sqlite` 实查：`cookies 1824 KB, 412 entries` | 日志说谎 |
| 4 | **首次纳入 `Local Storage/leveldb`**（跳过 `LOCK`） | 身份不完整 |

第 4 项的依据：H&M 的登录态不只在 cookie 里。实测用户 profile 的
`Local Storage/leveldb` 中 **22 个文件里有 3 个含 `hm.com`** 引用，只拷 cookie 得到的身份
H&M 仍会拒。

顺带补齐 `first_party_sets.db`、`Reporting and NEL`，并把文件清单提为常量
（`HM_IDENTITY_ROOT_FILES` / `_PROFILE_FILES` / `_NETWORK_FILES`）。

新增三个辅助函数：
- `countHmSessionCookies()` —— `node:sqlite` 只读查条数（Electron 41.7.2 已确认支持）
- `writeHmIdentityMeta()` / `readHmIdentityMeta()` —— 落 `.gsbot-identity-meta.json`
- `describeHmIdentityProblem()` —— 失败时给出人话指引

### 4.2 调用方分路提示

失败时不再静默，按 `hasUsableSession` 分两种情况：

- **旧身份还在** → `warning` 提示并**继续**（陈旧身份通常仍可用，直接失败反而弄坏本来正常的配置）
- **冷启动**（没有任何可用身份）→ 明确要求「完全退出 Chrome 再试」

## 五、其余三处根因（方向正确，但此前都被第四节的问题掩盖）

- **根因 #2（已修）**：`readListingPage` 在 `mode==='manual'` 时无条件短路到 Firecrawl，
  本地浏览器路径从未执行 → 已删除该短路，本地浏览器设为唯一主路径。
- **根因 #3（已修）**：session dir 被系统 Chrome 148 与内置 Chromium 147 交叉写入，
  触发降级清理 → `Code: 33 拒绝访问` → 已清理孤儿进程与锁文件。
- **根因 #4（已修）**：`prepareHmChromeProfile` 的 `.gsbot-chrome-cloned` 一次性标记
  → 已改为每次尝试刷新。
- **Firecrawl 对 H&M 完全不可用**：Akamai 直接封禁其出口，12 种参数变体全部 HTTP 500。
  已加 `HM_FIRECRAWL_KNOWN_DEAD = true` 常量记录该事实。

> 需要说明：#2 的短路、#3 的版本错配、#4 的一次性标记，三处修复方向都对，
> 但在第四节那个「身份从未到位」的问题解决之前，**它们的效果都无法体现**。

## 六、当前可复现状态

```
用户 Chrome 运行中   → 复制 EBUSY → cookieBytes=0 → 403（必然）
用户 Chrome 完全退出 → 复制成功   → 身份就位     → 预期 PASS
```

**复测方式**：完全退出 Chrome（含后台进程），运行 `tmp/hm-quiet-check.js`，
预期 `PASS`；或在 App 内直接重跑 H&M Men bestseller。

**注意**：`tmp/hm-quiet-check.js` 自身用的是**全新的空 profile**，不读 session 目录，
所以它验证的是「当前出口/风控是否放行」，而不是「身份复制是否成功」。
要验证后者，看 App 日志里的 `🔐 Chrome identity copied for H&M (cookies … entries)`。
